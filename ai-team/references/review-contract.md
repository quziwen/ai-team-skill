# AI Team 内部审阅约定

本约定使用 AI Team 现有 CCRL 做法。CCRL 负责固定审阅对象、保存原始意见、逐条回应及复核；任务安排、第三方判断和合并由 AI Team 负责。

## 怎样提出和回应质疑

先核对成果是否服务用户已确认的目标，不只检查文字和格式。质疑要有具体依据，说明会影响什么、建议怎样改；证据不足就说明还需核实什么，不把猜测当事实。没有实质问题就通过，不为显得独立而凑反对意见。作者和审阅者都按证据判断，不因对方或用户坚持就放弃有依据的结论；有新事实或发现自己出错时应修正。用户的偏好和目标由用户决定，不能当作事实错误来否定；合理取舍不强行争成对错。

## 审阅记录

### 最小任务交接与回报

主助手复用原有任务、成果和 Memo 编号，不另建一套工作流程。每次交接包含：用户任务原文；本身份负责及不负责的范围；所需依据的位置、版本或已计算摘要；允许的工具和写入文件；预期交付物；用户确认的完成标准；依赖是否已就绪。权限与分工备注不能改写用户任务。

任务状态、已确认结论和必要资料按本次工作提供，不默认转发全部聊天。来源发生变化时注明新旧版本，只重查受影响项。共享工作目录不是共享完整上下文；同时写同一文件时由主助手安排先后顺序，子 Agent 不覆盖他人修改、不自行再委派。

回报沿用成果和 Memo，附：产物位置及版本、实际执行的检查和证据位置、检查结果、未验证或未解决事项、需用户决定什么。失败也要回报，不拿旧输出冒充本次成功。已授权能补查的由主助手继续，只有缺材料、缺权限或业务取舍才问用户。

### 先核对任务要求

主助手保留同一份用户任务原文，发送给作者、审阅者和第三方时不改字句、换行或空格。分工说明、推测和协助备注与原文分开；备注不能新增验收要求。用户明确补充的要求单独保留，说明它与原文的关系并通知受影响会话，不静默覆盖旧要求。

如果双方引用的任务要求不一致，先核对各自实际收到的原文。主助手传错时，纠正副本并撤回由此产生的无效意见，保留原记录和纠正说明；只重查受影响内容，其他有效意见继续逐条处理。这属于输入纠正，不当作双方的专业分歧交给 C，也不冒充已经完成作者回应或复核。补发、重查若需要真实请求，仍计入原调用上限；额度不足时停止并确认，不能称为免费重试。

例如用户要求“完成标准和失败后的处理办法”，主助手不能转写为“验收方法和失败后的补救与重试路径”。作者可以提出重试建议，但须标为自己的建议，不能据此指责另一作者漏掉用户并未要求的内容。

包内 Runner 在同一子任务已有产出或初审记录时，会检查后续任务文字是否一致；复核请求从初审记录取回原任务。单独导入外部成果而没有此前任务记录时，只能以本次明确提供的原文开始核对。手动执行 Skill 的宿主不经过这段程序，仍须自行落实以上转交和检查，不能把程序测试当作模型已经遵守。

### 固定待审成果

每份成果记录 `artifact_id`、`assignment_id`、`author_id`、`version` 和正文。主助手负责准备固定版本并计算摘要，不把这个动作交给无命令权限的审阅者，也不要求模型凭文字猜出摘要。

主助手取得本次完整正文后，使用已有授权的本地能力计算，保留换行、空格和所有字符，不在计算前做格式转换。将同一份正文、成果编号、版本及计算结果一起交给审阅者；发送前核对正文逐字一致。读取文件不等于获准运行命令，不因为本规则擅自扩大工具权限。

- `content_sha256`：仅对正文的 UTF-8 字节计算 SHA-256，用于核对原文是否变化。
- `artifact_sha256`：沿用 CCRL 的 `artifact_sha256(Artifact)`，摘要还包括成果编号、子任务编号、作者和版本。Review Memo 的 `reviewed_sha256` 对应这个值，不拿正文摘要替代它。使用已有 CCRL 时继续由程序计算和校验，不改变旧格式。

可选工具：主助手将 `{"id":"成果编号","assignment_id":"子任务编号","author_id":"作者身份","version":1,"content":"完整原正文"}` 经标准输入送入 `python -B <skill-dir>/scripts/prepare_review.py`。这些字段由助手整理，用户不用填写。工具复用 CCRL 算法，默认返回不含 `content` 的 `artifact` 身份与版本信息、两种摘要及 `ready_for_review`；整个 JSON 最多 120 KiB，不读取任意路径、不写文件、不启动 Agent。只有退出码为 0 且 `ready_for_review=true`，才可继续交给审阅者；这只表示版本准备完成，不表示内容正确或审阅通过。

主助手在内存中保留输入的完整原文，核对返回的身份、版本和摘要，再将这份原文连同摘要交给审阅者。默认不在工具输出中重复正文，不能因此省略审阅者需要的全文。换行、空格和字符都必须保留；不要从终端截断输出拼回正文，也不要重新读可能已经变动的文件来替代已核对版本。

只有明确需要回显原文时，才使用 `--include-content`（Python 用法为 `prepare_review_input(payload, include_content=True)`）。该选项在成功时返回完整 `artifact`，可能使正文进入终端和工具调用记录；使用前确认这些记录的保存范围合适。默认成功输出及失败说明不回显输入正文；报错不代表可以把原始请求附进错误记录。主助手也不要把正文拼在命令参数、调试打印或报错附件中。身份字段只放不含业务正文的短编号，因为这些字段会出现在元数据中。

没有获准使用的计算能力时，明确记录 `needs_version_check`，保留草稿与已有意见，停止以完整审阅结果交付。不能让模型编造 SHA-256，不能把旧摘要、旧记忆或“不再报错”当作本次核对成功。`--hash-unavailable` 可供主助手记录此状态，退出码为 2 且不返回摘要；没有脚本运行能力时直接如实说明，不必强行运行。补齐条件后重新准备本次版本；超出原有授权才询问用户。

作者修改正文后，主助手为新版本重新计算；成果身份或版本变化也必须重新计算 CCRL 摘要。旧 Memo 与旧摘要保留，原审阅者复核的是新版本，不覆盖历史记录。

每份 Review Memo 固定记录审阅者、成果编号、版本、成果摘要（`reviewed_sha256`）、范围和完成标准。意见包含：

- `finding_id`：在本份 Memo 中唯一。
- `problem`、`evidence`、`suggestion`：具体问题、支持依据、修改建议。
- `severity`：critical、major 或 minor。
- 有分歧时补充主题及双方立场，不能删掉少数意见的事实依据。

没有发现问题时明确写 `no_findings`；读取失败、无法检查、缺少材料不能写成没有问题。原始 Memo 保留，后续处理追加新记录，不覆盖原文。

交付前按 [成果检查](delivery-checks.md) 留存各必要要求的实际检查依据、对应版本、通过／不通过／未验证及影响。检查记录附在现有审阅资料中，不另建一套评审；多数赞同、摘要相同、测试进程退出成功都不能代替具体检查结果。

双方都没有发现问题时，也执行这一步。Python 主流程接入 `delivery_requirements` 时，检查最新成果的全部必要项；存在 failed 或 pending 就在调用合并者前停止为 needs_verification，保留现有意见和成果，不把材料缺失伪装成观点分歧。纯 Skill 的主助手执行相同判断，但程序测试不证明宿主已经遵守。

## 回应和复核

### 同源材料与结论变化

对影响结果的具体主张，记录它依赖的原始来源、对应版本、引用位置和检查方法。两篇转载来自同一原文，或两个 Agent 都引用同一检索片段，只是同一依据被引用两次；不同网址、不同会话、不同模型都不能直接证明证据独立。无法追溯时写“来源关系未知”，不能由 URL 或文件哈希自动判定真实来源。

区分材料来源与检查方法：同一份原始表格由两人分别重算，可以提供计算上的交叉检查，但不能证明表格本身真实、完整；同一文档中不同原始记录也不应一概作废。按主张记录，不把整个 Agent 标成独立或不独立，不给同源材料机械降权、不累计分数决定胜负。

独立初稿及依据保留，不允许静默覆盖；后续可以改变结论，写清原结论、改后结论、导致变化的证据或推理纠正，以及影响的意见编号。纠正对已有材料的误读也有效，不强迫每次都找新资料。少数意见只要仍有有效依据，就必须逐条处理；多人同意不是撤回意见的理由。

作者对每条意见选择 accept、reject 或 clarify，并说明理由；接受修改时给出新的完整正文和版本号，不能只说“已修改”。原审阅者核对实际新版本，对每条意见确认已解决、撤回、仍有分歧或需要用户决定。

检查每条意见都恰好回应和复核一次，身份、成果和版本相符。缺项、重复项、换人、空正文或错版本必须停止。需要修改却没有实质改动，不能确认已解决。纯粹反驳或请求澄清时保留原成果版本。

## 第三方判断和合并

C 与争议双方不同，对每条剩余意见分别给出结论、理由和是否解决。无法核验的事实、用户未明确的预算或业务取舍，应保留为需用户决定，不能凭投票抹去。

先在原授权和次数内补查能取得的事实。到达次数或轮次上限、没有新材料、工具超时，都只是停止原因，不是“已解决”的依据。存在关键反证或必要材料缺失时保留 unresolved；C 说明还差什么、为何影响结果，不输出“高分观点胜出”的伪定论。仍保持一轮审阅、回应、原审阅者复核，之后才处理剩余分歧。

只把仍未解决的事项交给用户，包含双方观点、C 的判断及需要决定的具体问题。只要还剩一条未解决事项，就停止最终合并。已确认的部分保留为阶段成果。

没有剩余事项时，当前助手合并所有确认过的成果与第三方结论。Python `AITeam.run()` 还会检查确认正文是否被完整纳入，使用该程序时保持其检查规则；不要在程序外改写后声称仍通过原检查。

## 实际执行与本地示例

宿主子 Agent 的真实返回应作为本次任务记录。本地 Mock 只用于演示流程，不能补进真实作者回应、复核或第三方判断中。调用失败就记录失败；没有结果不能编造“通过”。

包内 Python 保留现有数据类型和校验实现，需要这些类型时从 `scripts/ai_team/contracts.py`、`ccrl.py` 和 `runner_backend.py` 读取；它们不是已连接的真实模型服务。

### 可选本地调用次数检查

`execution.py` 的 `TaskCallBudget` 是单任务、单进程、仅内存的可选记录。调用方在已获准范围内固定原任务、身份、动作、工具、已知模型与会话编号及次数上限，将同一个对象传给 `RunnerBackend(..., call_budget=...)`。一次性 CLI 初审可传给 `AuthorizedLocalCLIReviewRunner(..., call_budget=..., task=..., actor_id=...)`，仍必须提供原有单次 `approval`；不改变 Claude/OMP 限制。

程序在实际调用前占用一次额度，失败也不退还；拒绝原文不一致、未登记身份或动作、额度用完、重复调用编号及同身份同动作同内容再次执行。共享这个对象时不允许递归或并发调用；纯 Skill 的宿主原生并行方式不受此可选组件控制。超时或中断记为 `outcome_unknown` 并停止后续调用，先查实际执行状态，不自动重试、不换个编号重跑。不能通过新建对象或重启程序遗忘已用次数。

`report()` 只提供调用元数据：时间、耗时、身份、工具、已知模型和会话、请求摘要及状态；不导出正文或异常消息。token 和费用没有真实数据就为 null。`returned` 仅表示受包装的调用返回，`verification_status=not_assessed`、`proves_task_completion=false`；JSON 字段及业务检查仍由原流程另行完成。

它不自动发现工具、保留真实会话、确认实际底层模型或判断内容正确。指定会话时只核对返回的会话编号，编号一致不是会话保留的实测证明。未接入该对象的旧用法和宿主工具不受这些程序检查约束；它不替代用户授权，不是沙箱，不处理重启恢复、外部副作用撤销或不同进程间的重复执行。
