# 根据当前工具安排角色

## 先了解可用条件

以当前会话的可调用工具、参数说明和用户明确提供的信息为准。按工具分别记录所属模型、能否创建并继续独立会话、可保留的身份数量、可选模型或固定默认模型、同时可运行数量，以及可用文件工具。

只有能够创建独立会话并回到原作者、原审阅者继续回应时，才把 `independent_sessions` 填为 true。未知时填 false。`session_capacity` 是可保留并继续的不同会话数，未知填 0；`max_parallel_agents` 只表示同时运行数量。完整使用至少预留三个不同身份，可以顺序执行。

没有统一适用于所有工具的模型发现接口。Skill 由当前助手读取这些信息；本地分工脚本只接收这些信息，不自行探测服务、不读凭证。没有证据的能力标为未知。工具没有模型选择参数时填 `can_select_model=false`，并指明已知默认模型；多个模型已安装不代表当前工具能切换到它们。

### 分开确认模型选择和会话继续

- 工具提供 `model`、`provider` 或其他明确的模型选择入口，只说明本次请求可以指定目标。候选仍须符合当前可用信息和授权；参数存在不证明指定模型调用成功，也不证明会话能够保留和继续。
- 工具没有模型选择入口时，记录“不能通过当前工具直接指定模型”。默认模型有可靠记录就注明，没有就标未知；不能由参数缺失推断所有子会话必然使用同一模型。模型自报不能替代调用记录；请求记录中的模型编号也不证明服务实际使用了哪个底层模型。
- 多个工具分别连接不同后端时，核对每个连接的实际说明和返回，不仅凭工具名称判断模型。每个参与完整互审的工具还须能保留身份，并回到原作者、原审阅者继续工作。
- 只返回一次任务结果、没有已知会话继续办法的工具，不计入可保留会话数；即使可选多个模型也一样。一个原会话成功继续，不代表其他身份或完整互审流程都已通过。按 [真实验收说明](real-agent-acceptance.md) 分别保留证据，不为查明能力擅自发起真实调用。

不同模型不是完整使用的硬性要求。同一模型的三个独立会话可以满足使用条件，但可能有相似盲点；多个模型也不保证结果正确。

`availability` 只选当前原生工具 `native`、已具备可用连接的 `connected`、仅已安装的 `installed_only` 或当前不可用的 `unavailable`。后两类不能参与分工。模型始终跟所属工具一起选择；不同工具里的同名模型不能丢失来源。

| 当前条件 | 怎么安排 | 要说明什么 |
| --- | --- | --- |
| 独立会话，可选多个模型 | A、B 按任务所需能力选择，C 有分歧时再创建 | 按可用证据选择，模型名不代表专项能力 |
| 独立会话，只有一个模型 | 同一模型分别创建 A、B、C | 会话彼此独立，但可能犯相似错误 |
| 有独立会话，同时只能运行一个 | A、B 顺序工作，需要时再创建 C | 并发数量只影响速度，不改变审阅身份 |
| 无独立会话或情况未知 | 当前助手产出并自行检查草稿 | 独立互审尚未完成，不伪造第三方判断 |

只在任务已授权的工具中安排。不要因为其他模型可能更强就替用户注册账户、安装服务、修改登录状态或调用未确认模型。

## 防止沿用失效模型

- 每次开始新任务，都重新读取当前工具的模型参数和可用信息；有针对当前账户、当前工具的只读模型列表时，优先使用。历史聊天、旧配置、示例模型名和过去的成功记录不能替代当前可用信息；产品的通用模型列表也不能证明当前账户可用。不得把某个模型永久写成所有电脑的默认值。
- 工具允许省略模型参数、且没有明确选型要求时，优先使用本次已知可用的默认模型，不把内部的“当前默认模型”等描述当成真实模型编号传入。需要显式选择时，只用当前工具允许且符合本次授权的编号；信息冲突或无法确认时说明未知，不凭记忆猜测。不为核对可用性擅自增加真实探测调用。
- 新的 review 任务创建本次独立子会话，不沿用历史任务的子会话和模型设置。继续本次原作者、原审阅者时，先核对已有模型失败记录；省略模型参数不一定安全，因为旧会话可能仍保留失效设置。不能恢复原身份时按现有规则记录未完成，不能换个会话冒充原审阅者复核。
- 收到明确的模型不存在、已停用、该账户不支持或无权使用此模型的错误时，记录对应工具和模型，本次排除这个组合，即使工具的旧列表仍列着它也不重试。普通超时、限流、笼统的调用失败或未明确指向模型权限的登录错误，只记录本次失败及已知信息，不据此认定模型已失效，也不能断定故障与模型无关。不要因为一个工具拒绝，就把其他工具里的同名模型一起排除。具体报错与时间保存在本次测试记录，不写成所有安装者的长期规则。
- 只有本次已确认范围允许替换、仍有调用次数且存在当前可用选项时，才调整本次请求；不改全局或旧对话的模型设置，不跨到未授权的工具或账户。没有合适替代就明确停止。失败计入调用次数，不重跑已经完成的业务检查、不重复发消息，也不以自查冒充独立审阅。

如果主对话本身在读取 Skill 前就因模型不受支持而启动失败，AI Team 尚未运行，不能自救或保证不再报错。应明确区分这个工具启动问题与子 Agent 选择问题，不把更新 Skill 写成已经修复主对话。外部工具有当前可用模型选择或自动替换功能时，需由用户通过其受支持的方式处理；本 Skill 不修改相关配置。

## 分工与选择

新任务同时按 [任务与模型选择](task-routing.md) 准备可选的 `task_profile`。下面未带该字段的示例保留旧接口；它不检查任务风险或资料允许工具，不能用于宣称已完成这些检查。

### 保留能力依据，不先建新注册服务

每次分工在现有任务记录中补一份简短快照：检查时间、工具及已知版本、信息出处、当前可用模型说明、原身份继续办法、验证过的范围及记录位置。没查到的写未知；过期或矛盾信息先重查，不能把旧记录直接升级为本次可用。

软件已安装、账户认证状态、当前请求能否执行、原会话能否继续、完整互审是否验证，分别记录。认证状态只有现有工具明确返回且获准读取时才引用，不读取凭证、不为填表新增真实探测。一次命令成功不证明可继续三个会话；`measured` 也必须限定任务、版本和时间。

这份快照是助手准备的记录，不是让用户新增配置。已有能力清单够用就复用，不扫描 PATH、不新建常驻服务。角色仍按能力安排，不固定绑定历史 DSH、Claude 或 Codex 分工。

默认两位作者，职责互补：A 明确目标、原因、风险或内容结构；B 给出执行方案、实现、检查方法或质量意见。两人各交付一份成果并交叉审阅。主助手最后合并，不额外设一个润色 Agent。C 只在剩余分歧需要判断时启用。

使用主项目已有的任务划分能力标签。分工脚本复用 `CapabilityRouter`：代码任务偏向 analysis/risk 和 implementation/testing，写作任务偏向 writing/analysis 和 quality/testing，其他任务偏向 analysis/risk 和 delivery/testing。参与互审的模型还需要 review 能力。

先排除不可调用、不支持独立身份或不能选择的模型，再找能完成 A、B、C 的组合；有完整组合时，不为省一次调用退成缺少 C 的组合。组合内部先看能力覆盖和依据，最后比较已知成本。相同条件下优先让 A、B 使用不同模型；不为了凑不同模型而选择明显不合适的候选。能力说明不等于效果保证，只有在同类任务上做过检查的记录才标为 measured。

- `measured`：有可追溯的同类任务实测；只在记录支持的范围内填能力。
- `declared`：来自工具说明或用户明确指定，尚未做该任务的本地实测。
- `unknown`：能力不清楚；旧接口可作为暂定安排，带 `task_profile` 的新选择会排除。`general` 可表示已知存在但没有专项评测的通用模型，不能替代新增的复杂推理或高风险审阅要求。
- `cost_rank`：只比较当前信息中已知的相对成本，0 比 1 便宜；未知填 null，不猜价格。

C 必须是第三个身份和独立会话，不要求一定是第三种模型。缺少合适 C 时，已经达成一致的工作可继续；真正出现未解决分歧才交给用户。不能在主助手中模拟 C 的赞成票。

每位审阅者必须能接触被审正文和必要依据。没有该专业能力或无法读取资料时，说明哪些结论未被核验，不用表达流畅代替业务正确性。

## 当前助手填写的内部输入

将 JSON 经标准输入传给 `scripts/plan_team.py`，不要让用户手填。下面是虚构环境示例，不代表安装者拥有这些模型：

```json
{
  "task": "制定月结提效方案",
  "max_parallel_agents": 2,
  "tools": [
    {
      "id": "current-tool",
      "availability": "native",
      "independent_sessions": true,
      "session_capacity": 3,
      "max_parallel_agents": 2,
      "can_select_model": true,
      "current_model_ids": ["available-reasoner", "available-executor"],
      "unavailable_model_ids": [],
      "models": [
        {"id": "available-reasoner", "capabilities": ["analysis", "risk", "review", "arbitration"], "evidence": "declared", "cost_rank": 2},
        {"id": "available-executor", "capabilities": ["delivery", "testing", "review"], "evidence": "declared", "cost_rank": 0}
      ]
    }
  ]
}
```

返回的 `agent_id` 是本次建议的角色标识，`tool_id`、`model_id` 说明它应通过哪个工具使用哪个模型。创建成功后另记录工具返回的真实会话 ID。模型 ID 不能拿来冒充会话 ID。保留原作者和原审阅者会话，后续回应和复核回到原会话。

`current_model_ids` 由当前助手从本次取得的工具模型信息填写：有明确清单时填数组，明确没有可用模型时填空数组；无法取得时填 null，不把历史候选复制成“当前清单”。`unavailable_model_ids` 记录这个工具在本次任务中已经明确拒绝的模型，优先于当前清单。以上都由助手内部整理，用户不填参数。

本地分工脚本取候选与当前清单的交集，再排除已知不可用项；不会因为名单里有某个名字就虚构它的能力。默认模型固定且不可用时，不擅自换成其他候选。清单未知时保留原有按报告候选建议的方式，并明确实时可用性未验证；这不是显式传入未知模型编号的许可。

`independent_agents` 表示按已报告条件可尝试完整流程；`peer_review_only` 表示只有双人互审；`self_check_only` 表示只能当前助手自查；`unavailable` 表示不能安排出可用组合。`full_workflow_supported` 只是对输入条件的判断，`plan_only` 始终为 true，均不证明已经调用成功。

脚本不会检查账号可用性，也不会验证用户授权。真实执行前仍按本次具体任务确认调用上限和本地文件范围。两位作者各一次产出、审阅、回应、复核，最多八次子 Agent 请求；每次 C 判断和独立合并请求另计，失败也计数，多条意见造成的额外请求也计数。主助手按实际执行方式计算总额，不能把这个例子当成无限重试额度。

## 上下文、文件和结果

给每位作者同一份用户任务原文，并另列负责内容、协助备注、许可范围和必要资料。不得把主助手的解释写成用户原文，或用分工备注增加完成标准。发送前逐字核对；审阅和第三方判断也使用这份原文。不要把整个用户目录或历史聊天交给子 Agent。审阅者读取固定版本及原始依据，第三方同时看到双方意见、回应和缺失信息。

写代码时明确各自可以改的文件。工具无法隔离文件时，由一个执行者写入，其他人只读审阅。对文件修改发生重叠或输入版本变化的情况，重新核对待审版本，不直接覆盖。

工具不能恢复原会话时，保存真实返回内容作为本次记录，并明确独立身份无法保持；不要另开会话冒充原审阅者确认。优先使用支持恢复或追加消息的工具；确实做不到时列为未完成事项。
