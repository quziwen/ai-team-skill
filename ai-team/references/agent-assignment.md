# 根据当前工具安排角色

## 先了解可用条件

以当前会话的可调用工具、参数说明和用户明确提供的信息为准。按工具分别记录所属模型、能否创建并继续独立会话、可保留的身份数量、可选模型或固定默认模型、同时可运行数量，以及可用文件工具。

只有能够创建独立会话并回到原作者、原审阅者继续回应时，才把 `independent_sessions` 填为 true。未知时填 false。`session_capacity` 是可保留并继续的不同会话数，未知填 0；`max_parallel_agents` 只表示同时运行数量。完整使用至少预留三个不同身份，可以顺序执行。

没有统一适用于所有工具的模型发现接口。Skill 由当前助手读取这些信息；本地分工脚本只接收这些信息，不自行探测服务、不读凭证。没有证据的能力标为未知。工具没有模型选择参数时填 `can_select_model=false`，并指明已知默认模型；多个模型已安装不代表当前工具能切换到它们。

`availability` 只选当前原生工具 `native`、已具备可用连接的 `connected`、仅已安装的 `installed_only` 或当前不可用的 `unavailable`。后两类不能参与分工。模型始终跟所属工具一起选择；不同工具里的同名模型不能丢失来源。

| 当前条件 | 怎么安排 | 要说明什么 |
| --- | --- | --- |
| 独立会话，可选多个模型 | A、B 按任务所需能力选择，C 有分歧时再创建 | 按可用证据选择，模型名不代表专项能力 |
| 独立会话，只有一个模型 | 同一模型分别创建 A、B、C | 会话彼此独立，但可能犯相似错误 |
| 有独立会话，同时只能运行一个 | A、B 顺序工作，需要时再创建 C | 并发数量只影响速度，不改变审阅身份 |
| 无独立会话或情况未知 | 当前助手产出并自行检查草稿 | 独立互审尚未完成，不伪造第三方判断 |

只在任务已授权的工具中安排。不要因为其他模型可能更强就替用户注册账户、安装服务、修改登录状态或调用未确认模型。

## 分工与选择

默认两位作者，职责互补：A 明确目标、原因、风险或内容结构；B 给出执行方案、实现、检查方法或质量意见。两人各交付一份成果并交叉审阅。主助手最后合并，不额外设一个润色 Agent。C 只在剩余分歧需要判断时启用。

使用主项目已有的任务划分能力标签。分工脚本复用 `CapabilityRouter`：代码任务偏向 analysis/risk 和 implementation/testing，写作任务偏向 writing/analysis 和 quality/testing，其他任务偏向 analysis/risk 和 delivery/testing。参与互审的模型还需要 review 能力。

先排除不可调用、不支持独立身份或不能选择的模型，再找能完成 A、B、C 的组合；有完整组合时，不为省一次调用退成缺少 C 的组合。组合内部先看能力覆盖和依据，最后比较已知成本。相同条件下优先让 A、B 使用不同模型；不为了凑不同模型而选择明显不合适的候选。能力说明不等于效果保证，只有在同类任务上做过检查的记录才标为 measured。

- `measured`：有可追溯的同类任务实测；只在记录支持的范围内填能力。
- `declared`：来自工具说明或用户明确指定，尚未做该任务的本地实测。
- `unknown`：能力不清楚，只能作为暂定安排。`general` 可表示已知存在但没有专项评测的通用模型。
- `cost_rank`：只比较当前信息中已知的相对成本，0 比 1 便宜；未知填 null，不猜价格。

C 必须是第三个身份和独立会话，不要求一定是第三种模型。缺少合适 C 时，已经达成一致的工作可继续；真正出现未解决分歧才交给用户。不能在主助手中模拟 C 的赞成票。

每位审阅者必须能接触被审正文和必要依据。没有该专业能力或无法读取资料时，说明哪些结论未被核验，不用表达流畅代替业务正确性。

## 当前助手填写的内部输入

将 JSON 经标准输入传给 `scripts/plan_team.py`，不要让用户手填。下面是虚构环境示例，不代表安装者拥有这些模型：

```json
{
  "task": "制定月结提效方案",
  "max_parallel_agents": 2,
  "tools": [
    {
      "id": "current-tool",
      "availability": "native",
      "independent_sessions": true,
      "session_capacity": 3,
      "max_parallel_agents": 2,
      "can_select_model": true,
      "models": [
        {"id": "available-reasoner", "capabilities": ["analysis", "risk", "review", "arbitration"], "evidence": "declared", "cost_rank": 2},
        {"id": "available-executor", "capabilities": ["delivery", "testing", "review"], "evidence": "declared", "cost_rank": 0}
      ]
    }
  ]
}
```

返回的 `agent_id` 是本次建议的角色标识，`tool_id`、`model_id` 说明它应通过哪个工具使用哪个模型。创建成功后另记录工具返回的真实会话 ID。模型 ID 不能拿来冒充会话 ID。保留原作者和原审阅者会话，后续回应和复核回到原会话。

`independent_agents` 表示按已报告条件可尝试完整流程；`peer_review_only` 表示只有双人互审；`self_check_only` 表示只能当前助手自查；`unavailable` 表示不能安排出可用组合。`full_workflow_supported` 只是对输入条件的判断，`plan_only` 始终为 true，均不证明已经调用成功。

脚本不会检查账号可用性，也不会验证用户授权。真实执行前仍按本次具体任务确认调用上限和本地文件范围。两位作者各一次产出、审阅、回应、复核，最多八次子 Agent 请求；每次 C 判断和独立合并请求另计，失败也计数，多条意见造成的额外请求也计数。主助手按实际执行方式计算总额，不能把这个例子当成无限重试额度。

## 上下文、文件和结果

给每位作者任务、负责内容、验收要求、许可范围和必要资料。不要把整个用户目录或历史聊天交给子 Agent。审阅者读取固定版本及原始依据，第三方同时看到双方意见、回应和缺失信息。

写代码时明确各自可以改的文件。工具无法隔离文件时，由一个执行者写入，其他人只读审阅。对文件修改发生重叠或输入版本变化的情况，重新核对待审版本，不直接覆盖。

工具不能恢复原会话时，保存真实返回内容作为本次记录，并明确独立身份无法保持；不要另开会话冒充原审阅者确认。优先使用支持恢复或追加消息的工具；确实做不到时列为未完成事项。
