# 成果检查

交付时让用户知道检查了什么、用什么检查，以及哪些还没验证。作者、原审阅者和主助手在现有工作中完成，不另开 Agent，不增加真实调用，不让用户填写内部字段。授权不够就保留未验证状态。

## 在原记录上补检查结果

从用户已经确认的完成要求确定必要项，不擅自加条件，也不遗漏不容易检查的要求。保留原 ReviewPackage、Memo、回应和复核；检查结果引用对应成果编号、版本和摘要，不覆盖原始意见。

每项写清：要求是什么、检查对象和版本、实际检查方法、来源位置或测试记录、结果（通过／不通过／未验证）、未通过或未验证的影响。缺来源、没有执行、只有“大家都同意”，不能写通过。检查失败先交原作者修正，再由原审阅者复核；调用仍计入原有授权，本工具不会自动重试。

用户要求的是一份方案时，检查是否按要求交付方案；不能擅自追加“业务目标已实现”。方案中的预计效果保留为假设或待试用事项。例如“计划缩短一天”不因互审通过变成“已缩短一天”。

实际工具结果、材料自述、模型判断、未来目标分别说明。真实测试日志可记录执行命令、退出码、摘要及对应代码版本；没有执行就标未验证。引用原文存在，不等于它支持整段结论；数值相加正确，不等于数据来源、单位、期间或统计范围正确。这些仍由原审阅者检查。

必要项未通过或未验证时，只交付已确认的阶段成果并列明缺口，不宣布整个任务完成。不是所有缺口都要求用户决定：可以在原授权内核实的由助手继续，缺权限、材料或业务选择才问用户。可选建议、未来效果不冒充必要完成项，也不因此无故停止交付。

正常输出仍为原来六部分。把简短检查说明附在“审阅意见”或“最终成果”内，未解决的必要事项列在“未解决分歧”，注明是材料缺口、事实错误还是确有观点分歧，不强行交给第三方投票。用户不需要看 JSON 或哈希全文。

## 可选本地检查工具

`check_delivery.py` 只从标准输入读取最多 120 KiB UTF-8 JSON，不读取文件路径、访问 URL、执行命令、写文件或调用模型。来源必须由主助手在已有授权内取得并从内存提供。正文及来源不出现在报错里；成功结果保留要求、来源位置和检查摘要，不回显整篇正文。

输入包含 `artifact`、`review_package`、`checks` 三项。前两项使用现有 `Artifact` 和 `ReviewPackage` 格式，版本摘要仍按 CCRL 计算，不让模型猜哈希；不得为了通过本工具修改原完成要求。它们应是主助手已准备好的对象，不能拿来源不明的“通过”记录替代。所有 `review_package.acceptance_criteria` 都按必要项处理；漏交检查自动标为 pending，重复、额外要求、错版本或错摘要会拒绝。

第一小步仅支持：

| method | 检查内容 | 所需字段（另含 criterion、method） |
| --- | --- | --- |
| `sum` | 正文中独立一行的十进制加法等式，如 `12.30 + 7.70 = 20.00`；允许负数，最多 64 个加数，不做货币换算或业务判断 | `expression` |
| `source_quote` | 正文引用在提供的来源副本中是否逐字存在；记录该来源副本的摘要，不认证来源真伪 | `quote`、`source_ref`、`source_text`；来源为空则 pending |
| `unverified` | 保存尚不能验证的必要事项及影响 | `reason`、`impact` |

`criterion` 必须与原包中对应要求逐字一致。工具不能自动证明开放式方案、整份报告或代码已满足全部要求；它不支持的检查，不把要求改写成一个容易通过的算式或引用。由原审阅者结合真实证据检查并留存；未能检查时保留 pending。纯 Skill 或没有 Python 的工具也遵守上文记录要求，可用已授权的等效计算能力，不把缺少此脚本当成必须安装新平台的理由。

主助手可在 Python 内调用，用户不需要输入这些参数：

```python
from dataclasses import asdict
from ai_team.verification import verify_delivery

# artifact、package 是主助手已固定且相互匹配的现有对象。
receipt = verify_delivery({
    "artifact": asdict(artifact),
    "review_package": asdict(package),
    "checks": [{
        "criterion": "合计计算正确",  # 必须已经存在于 package 中
        "method": "sum",
        "expression": "12.30 + 7.70 = 20.00",
    }],
})
```

返回 `acceptance_status` 沿用 `AcceptanceCheck` 的 criterion、status、evidence，补充 method、source、source_sha256、impact，并固定成果版本和原 ReviewPackage ID。不要将结果混入原始 Memo 或修改旧记录。

- 退出码 `0`：所列客观检查通过，`checks_passed=true`。
- 退出码 `2`：至少一项 failed 或 pending；逐项查看 `blocking_criteria`，不得把进程正常返回解释成全部完成。
- 退出码 `1`：输入、版本或程序错误，未完成检查。

`proves_task_completion` 始终为 false：本工具不知道独立审阅是否完成、是否还有分歧，也不能证明业务实际效果。仅当原有审阅已完成、没有未决事项，且全部必要要求有适当的实际依据，才交付已确认成果。合并改动影响数字或引用时，固定最终正文的新版本并重查，不把子成果旧版检查直接搬过去当作最终版证明。

## 接到最终交付判断

Python 调用方可为 `AITeam.run()` 同时提供 `delivery_requirements` 与 `delivery_checker`，不增加 Agent 或模型请求。前者由主助手从用户已确认要求整理，并在产出前固定；必须列出每个子任务，值为必要要求的文字元组，没有额外客观检查时显式用空元组。不能为了容易通过删掉必要要求，也不能把可选建议、方案预计效果或尚未授权的业务实施改成必须完成。

`delivery_checker(artifact, package)` 接收经回应、复核后的最新完整成果及新检查包，返回上表格式的 `checks` 列表；核验仍由现有 `verify_delivery()` 执行。主流程重新计算当前版本摘要，原 Memo 与审阅包不改动；旧算式不在当前正文中、伪造通过回执、重复或多余要求、检查输入或执行错误均不能通过。回调是调用方已经获准的本地检查代码，不是新的权限或沙箱，不应在这里启动模型、联网或外部写入。

```python
result = team.run(
    user_task,
    delivery_requirements={"work-1": ("合计计算正确", "输入记录已核验"), "work-2": ()},
    delivery_checker=lambda artifact, package: [
        {"criterion": "合计计算正确", "method": "sum", "expression": "12.30 + 7.70 = 20.00"},
    ],
)
```

该例只有计算依据，缺少“输入记录已核验”的检查，应返回 `needs_verification`，保留成果和逐项检查，不调用合并者。没有提供回调也会保留全部必要项为 pending；读不到依据不能让回调凭自述补 passed。已有真正未决分歧时，仍按原流程停止，不能用客观检查覆盖争议。核对全部必要项通过后，才继续原有合并。

检查记录放在 `RunResult.delivery_verifications`，每份固定成果、版本、摘要和来源；用户仍看原来六部分，具体缺口列在“未解决分歧”，说明是证据缺口还是检查不通过。`needs_verification` 不等于一定需要用户裁决；能在原授权内补齐的由主助手处理，不能通过重跑忘掉调用记录。

省略上述参数时，旧 Python Mock 和 Phase 2 样例保持原行为，不能因此声称执行了必要证据核验。纯 Skill 宿主不经过此 API，主助手仍须实际落实以上检查。程序只核验明确提供的检查，不自动识别所有关键主张、认证来源、检查任意新增语句或证明业务效果。

两份转载都逐字匹配，只证明两次引用匹配，不能覆盖与原始记录的矛盾。`source_quote` 不识别转载关系，不自动判断证据独立性；原记录缺失时保留未验证，有反证时说明冲突及影响。所有 Agent 同意也不能填掉必要项的 pending。纠正后的正文应使用新版本重新核对，旧版检查与旧意见保留。
