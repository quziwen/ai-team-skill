# 真实 Agent 验收记录

本文件用于验证宿主是否真的创建并保留独立 Agent 会话。包内 `self_check.py`、Mock 演示、代码测试和“发现了 Skill”都不能替代该验收。

## 每次测试必须保留

- 测试时间、宿主名称与版本、操作端、Skill 版本与 ZIP SHA-256。
- 当前真实可选模型清单和失败模型；不得从旧对话推定。
- A、B、C 的真实会话或 Agent ID、各自角色、是否保留上下文、是否并行。
- 用户确认的调用次数上限、文件写入范围和外部动作权限。
- 每次调用的开始/结束状态、原始输出或可追溯链接、耗时、token/费用（宿主可提供时）。
- 交叉审阅意见编号、作者逐条回应、原审阅者复核，以及仍有分歧时 C 的判断。
- 主助手使用什么已获准工具准备待审版本；原正文、版本、`content_sha256` 和 CCRL `artifact_sha256` 是否匹配。至少验证一次“子 Agent 不执行命令，主助手完成摘要计算”；主助手也无法计算时，必须明确版本核对未完成，不能靠记忆跳过。
- 失败、重试和降级记录；失败调用也计入上限。
- 用户任务原文和实际发给各会话的任务副本是否逐字一致；分工备注是否另列，是否增加了用户未提出的完成标准。

分享记录前移除密钥、token、Cookie、个人目录、内部链接和敏感业务数据。

## 能力检查不能代替完整流程

分别记录“工具说明支持”“已发起并成功返回”“原身份已继续”和“完整流程已验证”，不要用一个通过结果代替其余项目。多次创建应保留不同 ID；并发只记录实际同时运行数量，未测到最大值就不称为并发上限。

单独验证会话保留时，先把一个无敏感信息的临时标记只交给被测子会话，完成后用原 ID 请它复述。第二次消息、附件或提示中不能再次提供标记或答案；若重新给出，只证明它读到了新消息。核对真实第二轮返回，不能把“消息已送达”当作完成。声称三个身份都已实测时，须分别有三个原 ID 的继续记录。普通业务任务仍只在出现分歧后创建 C，不能为凑记录自动增加调用。

模型选择能力来自实际工具说明；成功调用、使用的模型编号以及能否继续会话，各自需要相应记录。模型自报未知就保留未知；只记录请求编号时，不把它写成已核验服务内部实际模型。能力补测仍须在用户已确认的任务、角色和调用次数内执行。

## 三个必测场景

| 场景 | 真实前提 | 预期结果 | 不能声称 |
|---|---|---|---|
| 三会话完整流程 | 至少一个真实可用模型；三个可保留独立会话 | A/B 独立产出并互审；有未解决分歧才启用 C；关闭后由主助手合并 | 无 C 调用时不能写“C 已复核” |
| 两会话降级 | 只有两个可保留独立会话 | A/B 互审；未解决分歧交用户；标明 `peer_review_only` | 不能写“完整三方流程” |
| 无独立会话降级 | 零或一个独立会话 | 只给单助手草稿和自查；标明 `self_check_only` | 不能扮演多人并声称互审 |

## 结果口径

### 任务原文与耗时复测

使用同一份虚构任务、同一宿主和模型安排，比较修改前后记录。任务可包含“完成标准和失败后的处理办法”；检查主助手有没有擅自改成“验收方法和失败后的补救与重试路径”。如专门测试错误副本，使用明确标记的测试材料，不混入真实业务任务；确认系统先纠正副本，而不是增加 C 判断。测试和额外请求仍需事先授权。

分别记录分工准备、初稿、互审、回应、复核、合并和等待的开始/结束时间，保留总耗时、实际请求数、失败重试和可取得的 token/费用。并行调用耗时不可简单相加当作总耗时。确认有效问题没有漏掉、任务没有被改写、回应及复核完整后，再报告节省了多少时间；没有可比记录就标为“提速待实测”，不承诺从几十分钟降到固定分钟数。

### 怎样说明结果

- `本地自检通过`：仅包内确定性检查通过。
- `宿主流程通过`：上述三个场景在某个明确宿主版本真实运行并留证。
- `业务有效性待验证`：尚未由实际使用者在真实任务中评价质量、节省时间和复用价值。
- `正式验收通过`：只有事先约定的验收人、范围和标准全部满足后才能使用。

不同宿主、模型或版本要分别记录；一个宿主的成功不能外推到全部平台。
