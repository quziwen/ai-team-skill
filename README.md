# AI Team

给出一项任务，让几个 Agent 分工做、互相检查，最后交付一份完整成果。

AI Team 是一个多 Agent 协作 Skill。你不需要先研究该选哪个模型、安排多少角色或设置多少轮讨论，只需要说明要完成什么。

它会根据当前工具实际能调用的 Agent、模型和能力信息安排工作。角色不固定绑定某个厂商：适合分析的负责分析，适合执行的负责执行，适合审阅的负责检查。能力信息不足时，会明确说明哪些安排还需要试用验证。

它更适合需要认真核对的报告、方案和代码成果。简单问答或小段改写，通常直接问一个助手就够了，不必每次安排多人讨论。如果你明确要求互审，它也不能擅自改成单助手自查。

## 它怎样完成一项任务？

以“策划一场小型活动”为例：

1. **分工。** 一个 Agent 设计活动内容和时间安排，另一个补充人员分工、所需物品和备用办法。
2. **互审。** 双方检查对方的方案，看看有没有时间冲突、遗漏事项或难以执行的安排，指出问题并说明理由。
3. **回应和修改。** 作者逐条回应意见，修改后交回原审阅者复核，确认问题是否解决。
4. **处理分歧。** 比如双方对“活动内容是否过多”意见不一致，就请未参与争议的第三个 Agent，根据活动目标和可用时间作出判断，说明依据。
5. **交付。** 没有未解决分歧后，汇总成一份完整的活动方案；如果还有无法解决的问题，就把选项和理由列给你，由你决定后再定稿。

你看到的是分工、结果、审阅意见、讨论结论、未解决分歧和最终成果，不需要处理内部调用记录或配置文件。

## 至少需要几个 Agent、几个模型？

**完整使用的最低条件是：至少一个可用模型，以及能够创建、保留并继续使用三个独立子 Agent 会话的工具。** 主会话负责组织工作，三个子会话分别承担两位作者和一位必要时参与的第三方。

| 你现有的条件 | 可以怎样使用 |
| --- | --- |
| 能保留并继续使用三个独立子 Agent 会话 | 可以完成分工、互审、修改、复核和第三方判断 |
| 只能使用两个独立子 Agent 会话 | 可以分工和互审；双方解决不了的分歧直接交给你 |
| 不能创建独立子 Agent 会话 | 只能辅助起草和自查，不算独立互审 |

三个 Agent 可以使用同一个模型，也可以使用不同模型；不要求三个厂商、三个软件或同时运行三个 Agent。

不同模型可能提供不同视角，但不保证判断一定正确。同一模型的独立会话也可能犯相似错误，因此重要结论仍要看依据。

**电脑里装了几个 AI 软件，不代表它们已经能互相调用。** AI Team 只使用当前确实能调用、能取得结果的工具，不会把“已安装”当成“已接通”。

## 怎样安装和开始试用？

下载完整的 [ai-team.zip](https://github.com/quziwen/ai-team-skill/releases/download/v0.2.12/ai-team.zip)，解压后保留整个 `ai-team` 文件夹，不要只复制其中的 `SKILL.md`。

- 工具支持安装 Skill：按照该工具支持的方式安装完整文件夹。
- 工具不支持自动发现 Skill，但可以读取本地文件：让它读取 `SKILL.md`，并按要求读取附带说明。
- 工具不能读取所需说明，或不支持独立 Agent 会话：相关功能暂时不能使用，不能仅靠复制一段提示词补齐。

详细检查步骤见 [安装和试用说明](ai-team/INSTALL.md)。然后给它一项任务，例如：

> 请使用 AI Team，为一场虚构的 10 人、两小时室内交流活动制定方案。目标是让参加者相互认识，并完成一次小组讨论；不涉及采购、订场地或发送邀请。请给出活动内容、时间安排、人员分工、所需物品和备用办法。先说明这次如何分工、真实调用次数上限，等我确认后执行，结果只在聊天里展示。

建议第一次先用不含敏感信息的小任务，检查分工是否合理、审阅是否提出了实质问题、修改是否回应了意见。

阅读和使用 Skill 说明本身不要求安装 Python；运行附带的本地演示和检查脚本需要 Python 3.11 或以上。核对待审版本时，主助手需要获准使用的摘要计算工具，可以是包内脚本，也可以是当前工具提供的等效能力；没有可用能力时，会明确停在“版本核对未完成”。涉及代码开发时，还需要相应的文件操作和测试工具。

## 内置中文表达检查

作者、审阅者和最终整理者都会检查自己的中文表达：

- 删掉没有实际内容的开场、总结和客套话。
- 写清楚谁做什么、需要什么条件、怎样检查、失败后怎么办。
- 保留事实、数字、专业术语和必要限制，不为追求口语化改变原意。
- 不编造经历、人物、数字或引语。
- 不额外增加一次专门“润色”的模型调用。

目标是让文字自然、清楚、能直接拿来用，不是把所有材料都改成聊天口吻。

## 当前版本与使用限制

当前正式发布版本为 **v0.2.12**。

这次重点处理：**成果出来后补一句修改意见，不必把整项任务重做。**

- **原任务和补充意见分开保留。** 主助手判断影响范围，继续原作者和原审阅者；不能另开会话冒充原会话续接。
- **只修改受影响部分，但相关计算也要重查。** 例如把活动开场从20分钟改为10分钟，需要同步核对总时长，未受影响的人员和物品安排不重新生成。
- **新版本重新审阅，旧记录保留。** 不拿旧版通过记录替代新版检查。必要条件失败、缺依据或仍有分歧时，不强行交付。
- **重复意见不重复执行。** 可选本地接入在同一实例内返回原处理记录；错版本、修改越界、失败或中断时停止，不自动重试。

使用方法和限制见 [修改意见接续](ai-team/references/feedback-continuation.md)。用户不需要填写内部编号或参数；自然语言理解、影响范围和真实会话续接仍由当前主助手及其工具负责。附带 Python 接入只提供同一实例内的确定性检查，不自动解析任意意见，也不提供重启恢复、实时打断或多人权限。

v0.2.11 的必要证据检查继续保留：**几个 Agent 都同意，不代表结果就正确。**

- **先明确必要条件。** 把用户已经确认的完成标准与后续建议分开，不因审阅者提出建议就擅自增加要求。
- **检查最新成果，再决定是否交付。** 即使双方没有分歧，也要核对必要依据；作者修改后，旧版本检查结果不能直接沿用。
- **没通过就保留问题，不强行合并。** 可选 Python 接入在必要项失败或未验证时返回 `needs_verification`，保留阶段成果和检查记录，不调用合并者。缺证据不是让第三方投票就能解决的问题。

v0.2.9、v0.2.10 的改进也包含在本次发布中：主助手统一委派，不让子 Agent 无限制继续派活；独立初稿完成前不互看结论；重复转载不充当独立证据。任务分工先检查资料可以交给谁，再检查复杂程度、出错影响及实际能力，最后考虑已知成本，不把执行工作一律当作简单工作，也不按模型名字或价格猜能力。

这些做法不增加固定角色或默认讨论轮数。可选本地调用记录能检查经过它的请求、次数和重复执行，但不是所有宿主的统一控制，也不是授权或沙箱。默认 Mock 和旧调用方式保持兼容；省略新增检查参数时，不得声称已经核验全部必要条件。

v0.2.8 的成果检查工具继续保留：

- **检查对应到具体成果和版本。** 列出实际检查方法、来源或测试记录，以及通过、不通过、未验证的结果，不只写“已经检查”。
- **先核对能客观检查的内容。** 可选本地工具 `check_delivery.py` 能重算正文独立一行的十进制加法，核对引文是否在提供的来源原文中逐字存在。来源副本会计算摘要，但这不代表来源真实或完整。
- **没查清楚的事项如实保留。** 必要要求遗漏时不算通过；错版本、错摘要或伪造通过结果会被拒绝。工具不代替独立审阅，也不能证明整项任务完成或实际业务效果。

用法和限制见 [成果检查说明](ai-team/references/delivery-checks.md) 与 [任务和模型选择](ai-team/references/task-routing.md)。工具不读取输入中的路径和网址，也不执行其中的命令。它只能核对已提供的内容，不能认证来源、证明输入完整或自动发现所有关键事实。

v0.2.7 的任务一致性和减少重复工作的要求继续保留：

- **各 Agent 收到同一份任务原文。** 分工备注与用户要求分开写，不能擅自增加完成标准。后续请求与已有任务记录不一致时先停止并纠正，不能把输入错误当成业务分歧交给第三方。
- **独立工作可以同时做。** 工具允许时，同阶段互不依赖的两位 Agent 可以并行；继续原会话，集中处理有编号的意见，减少重复背景和频繁查询进度。
- **必要的检查不省略。** 审阅者仍要收到完整原文，作者逐条回应并修改，再由原审阅者复核。纠正输入需要新增真实调用时，也计入已确认的调用上限。

这是 Skill 的执行要求和本地程序检查，不是新增异步运行程序。实际能否并行取决于当前工具；本版没有进行真实耗时对比，不承诺固定的提速比例。

v0.2.6 的三项修正继续保留：

- **安装包检查更完整。** `self_check.py` 会检查清单外的额外文件，拒绝不安全路径和重复清单项。请用 `python -B` 运行脚本，避免产生缓存；旧版备份放在安装目录外。不要为了让检查通过而自行重算发布包清单。
- **待审工具默认不回显原文。** `prepare_review.py` 默认只输出成果身份、版本和摘要，需要输出正文时才显式加 `--include-content`。审阅者仍须收到同一份完整原文，不能只看摘要。
- **把工具能力和实际结果说清楚。** 能选模型不等于能继续原会话，一次性调用不计入可保留的子会话；没有模型参数也不能推定所有会话一定使用同一个模型。调用失败时保留原始错误，证据不足就不猜原因。

v0.2.5 的做法继续保留：由主助手准备并核对原文和版本，子 Agent 只读、不能执行命令，也可以参与审阅。如果主助手也没有获准使用的计算工具，就如实停止版本确认，不能沿用旧记录或编造摘要。

安装包还包含此前 v0.2.4 的本地自检脚本和真实试用记录模板；这些是检查工具，不是“真实 Agent 已通过”的证明。本版没有新增 Agent 角色或真实调用次数。

v0.2.3 的模型可用性检查继续保留：每次新任务重新核对当前工具的模型信息，不沿用旧对话或示例中的模型名。本地分工工具根据助手本次提供的模型清单排除旧候选和已知失败项；固定默认模型失效时停止，不擅自换模型。清单未知时明确实时可用性未验证，不自动发起真实探测调用。

**如果主对话在读取 Skill 之前就因模型不受支持而启动失败，AI Team 尚未运行，无法修复该对话的模型设置。** 本版不修改登录、全局模型配置或旧对话设置，也不保证服务永远不会报错。

v0.2.2 的两处工作要求继续保留：动手前发现方案偏离目标、假设没依据或明显做得过多时，说明理由并建议更小的下一步；审阅时有依据地质疑和回应，没有问题就通过，不凑反对意见，也不因对方坚持就改口。有新证据时及时纠正，用户决定目标和取舍。

v0.2.12 本地回归共 318 项，311 项通过、7 项因本机权限或系统能力限制而跳过、0 项失败；新增的31项修改接续测试全部通过。安装包自检及正常修改、错误合计停止、重复意见不新增执行三个本地演示检查通过，详情见 [本版测试范围](docs/releases/v0.2.12.md)。

本版未新增真实模型调用，也没有实测真实作者、审阅者的原会话续接。上一版 v0.2.11 曾用 skill-test v0.4.2 完成三个只读模型执行样例：正确合计正常合并；审阅者一致同意错误合计时停止合并；部分日期数据正确但整月依据缺失时停止合并。独立内容检查7项通过，实际工具记录检查3项通过，见 [v0.2.11 测试范围](docs/releases/v0.2.11.md)；该历史测试不覆盖本版新增的接续能力。

**本版演示和上一版模型样例中的作者、审阅者返回仍为本地预设 Mock，不代表真实 A、B、C 互审、修改、裁决全流程已验证。** 安装包自检通过也不等于所有 AI 工具和模型都已适配。v0.2.6 的两项脚本修复曾由两个独立 Agent 经 8 次请求完成互审和复核，该历史记录不覆盖后续新增改动。完整协作效果、长期稳定性、耗时和成本仍需在实际使用工具中验证；不承诺固定的提速或节省比例。

安装 Skill 不代表授权它调用其他模型或向外发送材料。真实执行前，会说明拟使用的角色、调用次数上限及本地文件操作范围；获得同意后，在该范围内继续工作。发布、发送消息和其他外部写入仍需单独确认。

本仓库用于分发 AI Team Skill。包内代码从 AI Team 主项目生成；CCRL 是其中的评审能力，不另建一套开发项目。
